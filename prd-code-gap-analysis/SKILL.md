# 需求与代码差异分析

## 定位

围绕一个有边界的需求主题，把“需求希望怎样工作”和“最新代码及当前数据能力实际支持什么”逐项对齐，输出可追溯的差异、未确认问题和变更范围。默认只读，不创建正式 PRD、ZSTT 阶段产物、技术方案或任务清单，也不修改业务代码或数据。

这个 Skill 不是把需求澄清和代码阅读机械串联。它负责两者之间的判定层：

```text
需求材料 → 原子需求与确认状态
最新代码与数据 → 当前行为、数据支持状态与证据
两者对照 → 一致、部分一致、确认差异、需求待确认、证据待补、不适用
确认差异 → 确定变更范围
```

始终区分以下事实类型：

- **原始需求事实**：材料或用户明确表达的内容；
- **已确认需求**：可以作为变更判断依据的当前有效口径；
- **未确认需求**：歧义、冲突、缺失边界或尚未获得用户确认的推断；
- **当前实现事实**：适用仓库、分支和提交中的源码、配置或契约直接证明的行为；
- **当前数据事实**：Schema、写入链路、查询链路和有边界的数据观察分别证明的数据结构、产生方式、可访问性和实际覆盖；
- **运行时事实**：有明确环境、身份和时间范围的日志或数据观察；
- **分析推断**：由证据支持但未被单一来源直接证明的关系。

需求材料不能证明功能已经实现，源码不能证明产品意图，表字段存在不能证明历史数据完整，一次运行记录不能代表全部场景，搜索无命中也不能证明代码或数据不存在。

## 与现有 Skill 的协作边界

- 需求材料能够提取稳定业务骨架时，直接执行本 Skill，不自动展开 `$prd-clarifier` 的完整澄清文档。只有材料散乱到无法确定目标、角色或核心行为时，才建议先使用 `$prd-clarifier`。
- 涉及仓库代码时，必须读取并遵循 `$read-code-with-codegraph`，由它确定最新 release / bugfix、代码来源、索引状态和安全回退；本 Skill 不复制或放宽其 Git 安全规则。
- 需求涉及实际数据覆盖时，完整读取 [Windows test DMS 取证](references/windows-test-dms.md)，由主 Agent 直接使用用户级 `aliyun-dms-mcp-server_test`。该 Provider 从 Windows 进程环境注入独立测试凭证，不依赖当前项目目录中的 `.env`、`.zstt-kit`、固定数据库映射或 `evidence_collector`，不要求用户再次授权或代为提供表、SQL、数据库记录，也不得自动切换或回退到 `prod`。
- 当前行为涉及产品、设备、内容、AI、语音或运行环境事实时，可使用 `$product-feature-analysis` 的有界功能模型和证据分类，但最终需求对照与变更判定仍由本 Skill 完成。
- 用户明确要求正式 ZSTT 需求、仓库调研或技术设计阶段时，使用对应 ZSTT Skill；不要用本 Skill 伪造 `00-requirement.md`、`01-research.md` 或 `02-design.md`。

## 工作流

### 1. 锁定分析边界

确认本次分析的需求主题、材料来源、目标读者、产品范围、仓库意图和需要回答的问题。记录不可读材料及其影响。

只有以下信息缺失到无法限定代码或数据调查时，才先提一个阻塞问题：

- 无法识别目标产品或功能对象；
- 多个仓库或版本会产生不同结论，且没有选择依据；
- 存在多个无法从代码、配置或连接信息区分的 test 数据源，且选择不同数据源会改变结论；
- 关键材料不可读，导致核心行为无法提取。

其他需求歧义先登记为未确认项，同时继续调查能确定的当前代码事实。不要因发现一个非阻塞问题就停止全部分析。

### 2. 建立原子需求台账

将材料拆成可分别验证的 `R01`、`R02`……，每项只表达一个行为或约束。至少记录：

- 来源及位置；
- 角色和对象；
- 触发条件或前置条件；
- 期望系统行为；
- 用户结果或外部副作用；
- 所需数据对象、字段、时间范围、粒度和覆盖范围；
- 范围、例外、权限、状态或验收边界；
- 确认状态与确认来源。

确认状态只允许：

| 状态 | 判定 |
|---|---|
| `已确认` | 原始材料明确且内部一致，或用户已经明确确认 |
| `待确认` | 存在歧义、缺少边界或需要用户选择业务口径 |
| `冲突` | 两个有效来源给出互不兼容的口径 |
| `推断` | 分析者为了理解而提出，尚不能当作需求事实 |

不要把代码当前行为倒推成产品需求，也不要把“通常如此”提升为已确认。一个句子包含多个角色、状态或结果时拆成多项，避免一个结论掩盖另一项差异。

### 3. 确认最新代码基线

对每个需要代码证据的仓库使用 `$read-code-with-codegraph`。在继续对照前，记录：

| 仓库 | 实际读取来源 | 目标分支 | 提交 ID | 最新性状态 | 局限 |
|---|---|---|---|---|---|

`实际读取来源` 必须明确是本地原有最新代码、远程 MCP、切换后的本地分支或其他已验证来源。无法证明分支和提交对应当前目标版本时，将相关结论标记为 `证据待补`，不得生成确定变更点。

按需求项组织代码问题，不用一个宽泛关键词扫描整个工作区。跨仓库时分别记录身份、版本和证据，不把一个仓库的提交状态推广到其他仓库。

### 4. 还原当前行为

从用户可观察入口追踪到最终行为点，并只收集回答对应需求项所需的证据：

1. Controller、Job、Consumer、页面事件或其他真实入口；
2. Service、Manager、Facade、RPC/HTTP Client 等实际调用链；
3. Repository、Mapper、SQL、缓存、ES、MQ、配置、计算或最终赋值点；
4. 真正影响结果的参数、状态、时间、权限、租户和上下文；
5. 用户可见结果、持久化结果或外部副作用；
6. 直接调用方、消费者和确有证据的影响边界。

Guard、判空和字段透传只作为定位线索，不能自动认定为真实业务依赖。列表、聚合、图表或映射补全场景必须核对最终实体集与 ownership、状态等映射的数据源范围是否一致。不得以测试断言、注释、DTO 字段名或相似方法单独证明生产行为。

代码关系不完整时回到源码、Schema、SQL 或接口契约验证。空结果、未索引、截断、超时、权限不足和动态调用未解析都属于证据缺口，不属于“不支持该需求”的证明。

### 5. 判断数据是否支持

需求涉及查询、筛选、统计、聚合、历史回溯、跨实体映射、数据写入或外部数据时，必须单独判断数据支持状态；与数据无关时标记 `不适用`，不要机械扩展。

先沿当前代码追踪到最终数据源，再分别核对三层能力：

1. **结构支持**：表、字段、索引、枚举、事件、缓存或外部接口是否能表达需求所需的数据；
2. **链路支持**：数据是否有真实生产、写入、更新、同步和读取路径，查询参数是否能到达最终数据点；
3. **实际数据支持**：现有数据的语义、粒度、时间覆盖、完整性、空值、隔离维度和更新时效是否满足需求。

数据支持状态只允许：

| 状态 | 判定 |
|---|---|
| `支持` | 结构、链路和需求所需的实际覆盖均有证据 |
| `部分支持` | 只支持部分对象、时间、范围、粒度或历史数据 |
| `不支持` | 有直接证据证明缺少所需结构、生产链路或数据覆盖 |
| `待补证` | 只能证明结构或代码路径，无法证明数据语义、填充率、历史覆盖或运行状态 |
| `不适用` | 当前需求不依赖业务数据能力 |

至少按需求实际涉及的维度核对：

- 权威数据源及字段业务含义；
- 主体、对象和关联键能否稳定映射；
- 数据粒度是否支持目标筛选或聚合；
- 租户、机构、权限、状态和时间范围是否覆盖；
- 历史数据是否存在，新增采集是否只能覆盖未来数据；
- 空值、重复、延迟、删除、归档和保留期限是否影响结果；
- 查询、索引、分页和批量获取是否可承受目标规模，避免循环内逐条数据库、RPC 或外部接口调用；
- 跨来源构建实体集与 ownership、状态等映射时，各来源范围是否有 Schema、查询或契约证明一致。

证据边界必须明确：DDL 或 DTO 只能证明结构，写入代码只能证明存在生产路径，查询代码只能证明可以访问；它们都不能单独证明已有数据完整。单条样本只能证明一次 occurrence，不能证明总体覆盖率。只有环境数据会改变结论时，才在用户授权的唯一环境执行有界只读检查，并仅输出脱敏统计或结构证据；不得暴露真实用户数据、Secret 或凭据。

#### Test 环境数据库核验

只要实际数据覆盖能够改变需求差异或变更范围，就完整读取并遵循 [Windows test DMS 取证](references/windows-test-dms.md)，由主 Agent 直接执行一个有边界的 `persistence-state` 数据库取证，不等待第二次确认。数据库凭证只能由用户级 DMS 启动器从 Windows 进程环境注入；主 Agent 不得读取、打印、复制或返回凭证值。

按以下顺序执行：

1. 先从适用版本代码、Mapper/Repository、SQL、Schema 和配置定位数据库、表、关联键、状态值、租户条件及时间字段；不要从需求名猜表或字段。
2. 锁定唯一 `test` 环境，以代码已经证明的 schema、表、字段、关联键和查询边界作为精确锚点，固定使用用户级 `aliyun-dms-mcp-server_test` 完成目标库发现、元数据核验和查询。
3. 把需求所需的数据事实改写为最小查询目标，例如总量、空值率、去重覆盖数、状态分布、最早/最晚时间、关联缺失数或目标范围内是否存在记录。
4. 优先执行聚合查询和脱敏统计；需要查看样本才能确认字段语义或关联关系时，只取最少行数和必要列，并隐藏用户身份、联系方式、内容正文、Token 等敏感值。
5. 查询条件必须来自需求范围或当前代码的真实关键参数。记录环境、数据库/Schema、表、选择条件、时间窗口、查询目的和脱敏结果，使数据结论可复核。
6. Windows 测试凭证缺失、DMS Provider 未注册、查询失败、超时、权限不足、目标库不唯一、表不存在或结果为空时，记录具体限制和最小继续动作；不得要求用户粘贴凭证，不得读取项目 `.env` 补救，也不得改用 `prod`。test 无数据只能证明该查询范围无样本，不能自动证明产品不产生该数据。

数据库操作必须严格只读。只允许为证据收集所需的 `SELECT`、安全元数据查看或等价只读能力；禁止 `INSERT`、`UPDATE`、`DELETE`、`REPLACE`、DDL、锁表、调用可能写数据的存储过程、创建临时对象或改变会话外状态。不要把连接地址、账号、密码、Token 或完整敏感记录写入输出。

test 数据可以证明 test 环境中的结构、样本覆盖和可查询性，不能单独证明生产环境的数据量、历史完整性或运行状态。需求依赖生产覆盖而当前仅有 test 证据时，分别写明“test 已证明什么”和“prod 仍未知什么”，不混成一个总体结论。

### 6. 逐项形成需求—代码追踪矩阵

每个原子需求必须且只能得到一个主结论：

| 主结论 | 使用条件 | 是否进入确定变更集 |
|---|---|---|
| `已一致` | 需求已确认，最新代码和相关数据证据证明当前能力完整满足 | 否 |
| `部分一致` | 需求已确认，当前实现或数据只满足其中可明确分离的一部分 | 仅未满足且已确认部分 |
| `确认差异` | 需求已确认，最新代码或数据证据证明当前能力与之不一致 | 是 |
| `需求待确认` | 业务口径为待确认、冲突或推断 | 否 |
| `证据待补` | 代码版本、调用链、最终行为或相关数据支持证据不足 | 否 |
| `不适用` | 有明确证据证明该需求不属于当前产品或仓库边界 | 否 |

矩阵至少包含：

| 需求 ID | 需求确认状态 | 期望行为 | 当前代码行为 | 代码证据 | 数据支持状态 | test 数据证据 | 主结论 | 差异或未确认点 |
|---|---|---|---|---|---|---|---|---|

确定变更点必须通过对应证据门禁：

1. 需求口径为 `已确认`；
2. 代码变更点由适用最新版本的代码证据证明，且当前行为与需求确实不一致；
3. 数据变更点由 Schema、生产/读取链路或有边界的数据证据证明，且当前数据能力与需求确实不一致。

数据相关需求只有在代码行为和数据支持均闭环时才能判定 `已一致`。已证明代码差异但数据仍待补证时，可以确认代码侧变更，把数据侧列为 `联动核查`；不得顺带断言需要或不需要改表、补数或迁移。`部分一致` 必须拆清已经支持和未支持的部分，不能把整项都算作新增。

### 7. 收敛未确认问题

将开放问题分为：

- `P0`：会改变核心范围、权限、状态、数据身份、接口契约或验收，阻塞确定变更范围；
- `P1`：影响重要行为分支、兼容或异常处理；
- `P2`：影响次要交互、文案或非阻塞细节。

每个问题应包含需求来源、已知代码或 test 数据事实、需要确认的具体口径、为何影响变更判断以及受影响的需求 ID。业务意图由用户确认；代码和可查询的数据事实继续由分析侧调查，不把“代码现在怎样”“test 库里有没有数据”反问给产品；设计选择留给后续技术方案，不伪装成需求问题。

只有未确认点会改变当前代码调查边界或使整体结论失真时，才在分析中途一次询问一个最关键问题。否则先完成其余矩阵，再集中输出问题清单。

### 8. 形成已确认变更范围

仅对 `确认差异` 和 `部分一致` 中已确认的未满足部分输出变更范围。每项至少说明：

- 需求 ID 和期望行为变化；
- 当前行为点及源码证据；
- 必须变化的职责、规则或契约；
- 有直接证据的仓库、模块、接口、DTO、服务、数据访问、配置或消息边界；
- 数据结构、采集/写入链路、历史覆盖、补数/迁移需求和查询性能是否属于确定变化或待核查；
- 需要联动验证的调用方、消费者、数据兼容和测试范围；
- 尚未证明、只能列为“待核查”的潜在影响。

把范围分为 `确定需变更`、`联动核查` 和 `无需变更`。只有源码已经定位到具体文件、类或方法时才写具体落点；否则写职责级范围和最小补证动作，不猜文件名或实现方案。

本阶段说明“哪里和什么行为需要变化”，不决定“具体怎样实现”。不要生成架构方案、SQL 草案、任务拆分、工期、提交或代码修改，除非用户另行明确要求进入对应下游任务。

## 输出契约

先给出一句话总判断，再按实际需要提供以下内容；简单场景可以压缩章节，但需求—代码追踪矩阵不能省略：

1. **分析范围与证据基线**：材料、仓库、代码来源、分支、提交、test 数据源和局限；
2. **需求理解摘要**：目标、角色、主流程和明确边界；
3. **需求—代码与数据追踪矩阵**：逐项期望、代码现状、数据支持、证据和主结论；
4. **待确认问题**：P0/P1/P2、影响需求和确认原因；
5. **已确认变更范围**：确定需变更、联动核查及对应证据；
6. **当前已支持或无需变更**：防止重复建设；
7. **证据缺口与下一步**：只列解除当前代码或数据未知所需的最小动作。

代码证据使用可点击的仓库文件与行号；远程证据说明仓库、分支或提交、文件路径、符号和定位限制。数据证据说明 `test` 环境、数据库或 Schema、表、选择条件、时间窗口和脱敏统计，不暴露连接信息或敏感记录。明确区分需求原文、代码事实、test 数据事实与分析推断。

## 停止条件与禁止事项

- 当全部需求项已有主结论，或剩余未知无法通过有界读取解除时停止；不要为追求表面完整度无边界搜索。
- 默认只在聊天中交付。用户未要求保存时，不创建分析报告、需求文档或阶段产物。
- 不修改业务代码、配置、数据库、需求权威文档或 Git 历史。
- 不把待确认需求提前写成确定变更点，也不使用无证据的兜底设计掩盖需求或数据源问题。
- 不诊断缺陷或提出修复；若证据显示可能违反既有契约，只陈述预期、实际、证据和缺口，并建议转入缺陷分析。
- 不自动进入需求澄清、技术设计、任务拆分、实现、测试、提交、推送或部署。
