# 使用 CodeGraph 阅读代码

## 核心规则

- 先确定要读取的目标分支及其远程最新提交，再选择本地 CodeGraph、远程 CodeGraph 或安全切换本地分支；不要默认当前检出分支就是最新代码。
- 先用 CodeGraph 定位符号、调用链和影响关系，再按定位结果读取源码。
- 把 CodeGraph 当作导航证据，不把索引关系当作最终事实；关键结论必须由当前源码验证。
- 除获取远程引用、刷新仓库内的 `.codegraph` 索引以及本技能规定的安全分支切换外，保持只读。没有独立授权时，不修改业务代码。
- 如果用户明确禁止刷新索引或禁止写入 `.codegraph`，遵从用户要求并说明分析局限。
- 不执行 `stash`、`reset --hard`、强制切换、丢弃修改或删除分支。工作区不干净、目标分支有分叉或最新分支无法唯一确定时，停止切换并请用户处理或确认。

## 工作流

### 1. 确认仓库、远程和工具

1. 定位当前任务所属的 Git 仓库根目录，并在该目录执行 CodeGraph 命令。
2. 使用 `git remote get-url origin` 确认远程仓库身份；后续远程 MCP 结果必须与该仓库匹配。
3. 确认本地 `codegraph` CLI 和远程 `mcp__codebase_remote_read__codegraph_explore` 是否可用。
4. 如果本地 CLI 不存在，不要自行安装；本地代码已最新时改用 `rg` 和源码阅读，未最新时继续尝试远程 MCP。

### 2. 确定最新目标分支

先执行 `git fetch --prune origin` 更新远程引用。该命令只更新 Git 元数据，不切换分支；如果获取失败，不能声称已经确认最新分支。

按以下优先级确定目标分支：

1. 用户明确指定的分支或版本最高优先级。
2. 用户未指定时，从 `origin` 下名称以 `release/`、`release-`、`bugfix/` 或 `bugfix-` 开头的远程分支中选择。
3. 分支名包含可比较的语义化版本时，优先选择版本最高者；同版本候选按远程分支尖端提交时间选择较新者。
4. 分支名没有可比较版本时，按远程分支尖端提交时间选择最新者。
5. 如果版本格式冲突、多个候选无法可靠排序，或没有匹配分支，不擅自退回默认分支，说明候选并请用户明确目标。

可使用以下只读信息完成判断：

```text
git for-each-ref --sort=-committerdate --format="%(refname:short)|%(objectname)|%(committerdate:iso-strict)" refs/remotes/origin
git rev-parse HEAD
git rev-parse refs/remotes/origin/<目标分支>
git status --porcelain=v1 --untracked-files=all
```

只有同时满足以下条件，才将本地工作树视为可直接读取的最新代码：

- `HEAD` 与 `origin/<目标分支>` 指向同一提交；
- 当前工作树没有会改变待分析源码的未提交修改；
- 能明确记录目标分支名和提交 ID。

本地存在领先提交、分叉提交或源码修改时，都不能把它当作远程最新版本。保留这些修改，不做自动清理。

如果 `git fetch` 失败，可以尝试远程 MCP；但只有远程结果自身能证明仓库和版本时才能作为最新代码。缓存的远程引用只能标记为“最近一次已知状态”，不能据此自动切换并宣称最新。

### 3. 选择代码来源

```text
本地 HEAD 等于目标远程提交且源码未被修改
  → 使用本地 CodeGraph，并检查本地索引
否则
  → 优先使用远程 CodeGraph MCP
      → 远程仓库和目标版本可验证：直接读取远程结果，不切换本地分支
      → 远程不可用、未索引、结果过期或版本不可验证：安全切换本地分支后读取
```

#### 3.1 本地代码已最新

进入“检查并刷新本地索引”，随后使用本地 CodeGraph 查询。

#### 3.2 本地代码不是最新：优先远程 MCP

调用 `mcp__codebase_remote_read__codegraph_explore`：

- 根据 `origin` URL 规范化出的组织、路径和仓库名，匹配 MCP 已配置的 `repository`；能唯一匹配时显式传入 `repository`。
- 无法直接匹配时，可省略 `repository` 做一次全仓搜索，但查询中必须包含唯一仓库标识、目标分支、目标提交和用户问题；结果仍须回到正确的仓库分组。
- 查询应同时包含用户要分析的符号或业务问题，以及目标分支名和目标提交 ID。

只有满足以下条件，才能把 MCP 结果当作目标分支源码：

1. 返回的仓库身份与本地 `origin` 一致；
2. 返回元数据明确显示目标分支或提交，或者把结论依赖的关键源码与 `git show origin/<目标分支>:<文件路径>` 逐项核对后内容一致；
3. 响应没有未解决的索引冻结、未同步或文件过期警告；
4. 返回内容覆盖本次结论所需的入口、调用链和最终数据点。

仓库未配置、工具调用失败、结果为空、命中其他仓库、版本无法验证或索引过期，都属于远程读取不可用。不要用不明版本的 MCP 结果冒充最新代码。

#### 3.3 远程不可用：安全切换本地分支

切换前在 commentary 中说明目标分支、目标提交以及即将改变本地检出状态，然后执行安全检查：

1. `git status --porcelain=v1 --untracked-files=all` 必须为空；否则停止，不自动暂存、提交、清理或覆盖用户修改。
2. `origin/<目标分支>` 必须存在，并且来自本次成功的 `git fetch`；否则停止。
3. 本地存在同名分支时，先 `git switch <目标分支>`，再执行 `git merge --ff-only origin/<目标分支>`。
4. 本地没有同名分支时，执行 `git switch --track -c <目标分支> origin/<目标分支>`。
5. 快进失败或本地分支已经分叉时停止；不使用强制更新、重置或删除分支。
6. 切换后再次确认 `HEAD` 等于 `origin/<目标分支>`，再检查并刷新本地 CodeGraph 索引。

最终输出必须说明实际读取来源是“本地原有最新代码”“远程 MCP”还是“切换后的本地目标分支”，并给出目标分支和提交 ID。

### 4. 检查并刷新本地索引

先执行：

```text
codegraph status --json .
```

执行任何 `init`、`sync` 或 `index` 前，先在 commentary 中告诉用户原因以及会更新仓库内的 `.codegraph`。

按状态处理：

| 状态 | 操作 |
|---|---|
| `initialized` 为 `false`，或仓库没有索引 | 先告知用户会创建 `.codegraph`，再执行 `codegraph init .` |
| `pendingChanges` 中任一数量大于 0、`worktreeMismatch` 非空，或索引状态不是 `complete` | 先告知用户会更新 `.codegraph`，再执行 `codegraph sync .` |
| `reindexRecommended` 为 `true`，或增量同步后仍无法得到完整索引 | 执行 `codegraph index .` 全量重建 |
| 索引完整且没有待同步变化 | 直接使用现有索引 |

刷新后再次执行 `codegraph status --json .`。只有索引状态完整、待同步变化归零后，才把它视为当前代码的有效导航索引。若刷新失败，说明失败原因并使用源码搜索补足，不得假装索引最新。

### 5. 优先查询 CodeGraph

根据问题选择最少的一组命令，不要机械地全部执行：

- `codegraph query <关键词>`：定位类、方法、接口或路由。
- `codegraph explore <问题或主题>`：一次查看相关源码片段和主要调用路径。
- `codegraph node <符号或文件>`：查看精确符号、源码位置及相邻关系；存在同名符号时用 `--file <路径>` 限定文件。
- `codegraph callers <符号>`：查上游调用者。
- `codegraph callees <符号>`：查下游调用。
- `codegraph impact <符号>`：仅在用户询问修改影响或风险时分析影响面。
- `codegraph affected <文件...>`：仅在需要定位受影响测试时使用。

通常按“关键词查询 → 精确符号 → 上下游调用”的顺序收敛。优先围绕用户问题中的入口、业务方法和最终数据访问点查询，避免无目的遍历整个仓库。

如果接口、实现类、Facade 或重载方法存在同名符号，按简单名称执行 `callers` 或 `callees` 可能合并多组关系。此时把结果当作候选集合，使用 `node --file` 消歧并回到对应源码逐条确认，不得直接据此判定调用方向。

### 6. 回到源码验证

按照 CodeGraph 给出的文件和行号，以 UTF-8 读取当前源码，并完成以下核验：

1. 找到真实入口和直接执行路径。
2. 追踪到最终查询、RPC、外部接口或计算点。
3. 确认真正影响结果的参数和数据源。
4. 区分守卫条件、空值检查与真实业务依赖。
5. 对跨实体映射、动态调用、反射、生成代码或 CodeGraph 未解析关系，使用 `rg` 和源码继续验证。
6. 分析分支差异时，先用 Git 确认变更文件和基线，再确认这些文件已被所选来源的最新索引覆盖。

不得仅凭符号名称、注释、单条图关系或调用方猜测业务结论。

### 7. 输出结论

先给结论，再提供必要证据。至少说明：

- 入口或触发点；
- 实际读取来源、目标分支和提交 ID；
- 实际调用链；
- 最终数据源或计算点；
- 关键参数；
- 受影响的直接调用者或模块；
- CodeGraph 未覆盖或需要人工复核的部分。

明确区分“CodeGraph 显示的关系”“源码直接证明的事实”和“基于证据的推断”，并引用可点击的源码文件与行号。

## 示例

用户询问“最新 release 分支中的学习轨迹导出逻辑从哪里取数”时：先更新远程引用并确定最新 release 分支及提交。如果本地正好位于该提交，检查本地索引后查询 `exportTracksByUserIdsAndLearningDate`；如果本地落后，先尝试远程 MCP 并验证仓库与版本，远程不可用时仅在工作区干净且能够快进的情况下切换目标分支。随后读取定位到的 Service、Facade 与 Repository 源码，最终说明读取来源、分支、提交、入口、实际取数 Facade、补充用户信息的数据源及关键参数。
