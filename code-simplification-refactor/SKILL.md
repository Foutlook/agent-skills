# 代码简化与重构

执行 Claude Code `/simplify` 风格的 cleanup-only review：审查当前改动，汇总四个独立视角的发现，并直接应用可证明行为不变的清理。不要把它扩展成 correctness bug、security 或业务逻辑审查。

## 默认语义

- 默认执行并修复，不先停在报告或方案阶段。
- 仅当用户明确说“只看”“评审”“给建议”“不要修改”时切换为报告模式。
- 不为安全清理逐项请求确认。跳过不确定或可能改变行为的项，继续应用其余安全修复。
- 保持接口契约、业务语义、数据范围、返回结构、兼容性、异常行为和调用时机不变。
- 清晰优先于行数更少。拒绝难读的一行式写法、嵌套三元表达式和单次使用的过度抽象。
- 只处理选定范围及证明复用所需的最小相邻上下文，不顺手重构无关模块。
- 遵守仓库中的 `AGENTS.md`、`CLAUDE.md`、既有风格、测试约定和构建方式。
- 保留与本次清理无关的注释；移动代码时连同相关注释一起移动。

## 1. 确定范围

按以下优先级选择范围，并在开始时用一句话说明：

1. 用户指定文件、目录、类、方法或其他符号：定位定义后读取完整文件；再按需读取直接调用方、测试和候选复用实现。不要只看该符号所在的 diff 片段。
2. 用户指定提交、提交数量、分支、PR 或日期范围：使用对应的 `git show` 或 `git diff`。
3. 用户未指定范围：读取 `git status --short`、未暂存 diff 和暂存 diff，以全部当前改动为范围。
4. 当前没有未提交或暂存改动：自动审查 `HEAD` 最近一次提交。

忽略未被范围包含的历史代码和无关未跟踪文件。若当前目录不是 Git 仓库且用户未指定目标，才询问范围。

## 2. 四路独立审查

默认同时启动四个审查单元，让它们读取同一份完整范围。环境支持子 agent 时必须并行派发；环境不支持时，由当前 agent 按四个独立视角完成，并在汇总前避免互相覆盖结论。

每个审查单元只报告 cleanup 问题，提供文件位置、证据、维护成本和最小清理方案。

### Code Reuse

查找当前改动是否重复实现了仓库已有能力：helper、组件、mapper/repository/service 方法、转换器、枚举、校验、格式化逻辑或同类模式。只有语义、数据范围、异常和边界条件等价时才复用；名字相似不是证据。

### Simplification

查找冗余状态、中间变量、重复分支、深层嵌套、copy-paste、死代码、无用兼容层和可读性差的控制流。简化后必须更容易理解，不能只追求更短。

### Efficiency

查找当前改动引入的明确浪费：重复计算或对象构造、重复序列化、循环内 DB/RPC/API 调用、可复用结果被反复获取、不必要的并发容器或阻塞初始化。涉及数据访问范围、并发语义、缓存一致性或调用时序的变化不自动修复。

### Abstraction Level

检查职责和抽象层级是否合适：业务规则是否落入 Controller，通用校验是否散落在 Service，底层工具是否依赖上层对象，局部 fallback 是否掩盖数据源或机制问题。优先最小闭环修正，避免扩散补丁分支。

## 3. 汇总并应用

合并四路结果，去重并核验证据。按以下规则处理，不因存在跳过项而暂停安全修复：

| 结论 | 处理 |
|---|---|
| 行为不变、证据充分、范围可控且可验证 | 直接应用 |
| 可能改变行为、兼容性、数据范围、异常语义或调用时机 | 跳过并说明 |
| 需要大范围架构调整、证据不足或缺少必要测试保护 | 跳过并说明 |
| 疑似 correctness、security、并发竞态或业务逻辑 Bug | 不调查、不修复；简短记录并建议改用 code review、security review 或调试流程 |

跨文件不等于高风险。若跨文件修改只是复用已证明等价的现有实现，且仍在最小闭环范围内，可直接应用；只有行为风险或范围明显扩大时才跳过。

应用时优先使用项目已有模式，不新建单次使用抽象。简单 getter、常量和清晰的一层调用可保持 inline；仅为复杂表达式、复用值或调试价值提取局部变量。禁止用猜测性的 fallback 掩盖证据不足。

后端项目还需守住这些边界：

- 禁止把循环单查改成另一种 N+1；批量读取必须证明数据范围一致。
- 聚合、图、统计和映射逻辑不得混用未经证明等价的数据源。
- Java DTO/VO/Request/Response 的 `zValue`、`pType`、`uId` 等 JavaBean/Jackson 高风险字段，只有在本次范围涉及绑定时才显式核验 `@JsonProperty`，不要借 cleanup 改接口字段名。
- 不删除或改写与当前清理无关的注释。

## 4. 验证

检查最终 diff，确认每一处修改都来自汇总后的安全 cleanup，且没有意外注释丢失或范围扩张。运行与改动最接近的测试、编译或静态检查；无法运行时说明原因和剩余风险。

Maven 后端项目若 smart-doc 绑定早期生命周期，而目标只是验证代码或单测，优先添加 `-Dsmart-doc.phase=verify`。

## 输出

简洁报告：审查范围、已应用的清理、跳过项及原因、验证结果。没有安全清理项时，直接说明当前范围已经足够干净，并确认四个视角均已检查。

不要输出冗长的执行前审批表，除非用户明确要求报告或计划。不要把疑似 Bug 混入“已修复”清单。

## 边界

- 找逻辑 Bug、回归或空指针：使用 code review 或调试类 skill。
- 找漏洞、权限和安全风险：使用 security review。
- 实现新需求：先完成开发，再用本 skill 清理增量改动。
- 大规模模块重构：先拆解方案和风险；本 skill 只负责每批改动后的 cleanup。
