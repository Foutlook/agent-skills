# 代码简化与重构

这个 skill 用于做 `/simplify` 风格的代码清理：先确定审查范围，再从复用、简化、效率、实现层级四个角度找维护成本，最后只应用行为不变、范围可控、证据充分的改动。

它不是常规 bug review。不要主动寻找业务正确性、权限漏洞、并发竞态或安全问题，除非这些问题直接来自“简化/重构”动作本身。目标是让已有行为用更清晰、更一致、更低维护成本的方式表达。

## 核心原则

- 保持功能不变。任何会改变接口契约、业务语义、数据范围、返回结构、兼容性或调用时机的改动，都先跳过并说明原因。
- 清晰优先于行数更少。不要把代码压成难读的一行、嵌套三元表达式或过度抽象。
- 只处理用户指定范围或最近修改范围。不要顺手重构无关模块。
- 先找证据再动手。复用已有工具、抽象或数据源前，必须从代码、查询、接口契约或调用链中确认它确实等价。
- 保留相关注释。不要清理、改写或删除与本次变更无关的注释；修改非平凡逻辑时补充必要的“为什么”注释。
- 尊重项目规则。优先阅读并遵守仓库中的 `AGENTS.md`、`CLAUDE.md`、现有编码风格、测试习惯和构建方式。

## 触发后流程

### 0. 选择执行模式

先根据用户措辞确定执行模式，并在开始时说清楚：

- `报告模式`：用户说“只看一下”“给建议”“评审”“不要改”时，只输出发现项、分级和建议，不修改文件。
- `安全修复模式`：用户要求“简化”“重构”“清理”但没有明确授权高风险改动时，默认只处理 `可直接改` 项。
- `确认后修复模式`：用户明确要求执行较大重构，或第 3 步出现 `需确认` 项时，先列出计划并等待确认，再继续修改。

如果用户的目标不清楚，先按 `报告模式` 审查并给出下一步选择；不要因为“重构”两个字就默认做跨模块大改。

### 1. 确定审查范围

根据用户输入选择最小可闭环范围：

- 用户给了文件、目录、提交、分支、PR、日期范围或说明：以该目标为准。
- 用户说“最近修改”“当前改动”“简化一下”：优先查看 `git status`、`git diff HEAD`、`git diff --cached`。
- 用户说“最近一次/几次提交”：使用对应的 `git show` 或 `git diff` 范围。
- 有 upstream 时，可用 `git diff @{upstream}...HEAD` 查看分支差异；没有 upstream 时再考虑 `main...HEAD`、`master...HEAD` 或 `HEAD~1`。

把范围说清楚：本次会审查哪些文件/提交/未提交改动，以及哪些内容不在范围内。

### 2. 四角度审查

如果可用并且任务规模值得并行，使用子 agent 或并行检索分别从四个角度审查；否则由当前 agent 逐项完成。每个发现项都要给出文件、位置、问题摘要、维护成本和建议的更简单形式。

#### Reuse：复用

寻找新代码是否重新实现了已有能力：

- 已有工具类、组件、mapper/repository/service 方法、DTO 转换器、枚举能力、通用校验或格式化逻辑。
- 相邻文件中已存在的同类模式。
- 同一业务规则在多个类中重复表达。

只有在确认语义、数据范围和边界条件等价时，才建议复用。不要因为名字相似就替换。

#### Simplification：简化

寻找不必要的复杂度：

- 冗余状态、派生字段、双写字段、无实际用途的中间变量。
- copy-paste 后只有细微差异的代码。
- 深层嵌套、过长分支、可早返回但未早返回的流程。
- 死代码、未使用方法、临时兼容逻辑遗留。
- 过度防御式空判断，但要先确认数据来源契约确实保证不为空。

建议的简化形式应更容易读和维护，而不是单纯更短。

#### Efficiency：效率

寻找新增的浪费：

- 循环中重复 DB/RPC/外部 API 调用，尤其是 N+1 查询。
- 重复计算、重复序列化/反序列化、重复构造大对象。
- 可以并行的独立 I/O 被串行执行。
- 在启动路径或热路径中加入阻塞或重型初始化。
- 长生命周期对象捕获过大的闭包/上下文，导致不必要的内存持有。

优先给出批量查询、预加载、映射缓存、惰性加载或更小对象边界等替代方案。

#### Altitude：实现层级

检查改动是否放在正确抽象层：

- 是否用局部特判掩盖了底层机制缺陷。
- 是否在 controller/service/repository/DTO/枚举之间放错了职责。
- 是否本该修正数据源一致性，却增加了 fallback 或并行查询。
- 是否本该抽出业务规则，却散落到多个调用点。

优先选择最小闭环的底层修正，而不是扩散更多补丁分支。

### 3. 去重、分级与检查点

汇总发现后先去重。相同机制导致的问题只保留一个修复计划，并按风险分成三类：

- `可直接改`：局部、行为不变、证据充分，且有明确验证方式。
- `需确认`：跨文件抽象、删除兼容字段、调整公共组件、批量替换调用点，或测试保护不足但收益明显。
- `只建议`：会改变既有行为或兼容性、需要大范围架构改造、证据不足，或超出用户指定范围。

进入修改前先向用户说明分级结果；如果全部都是 `可直接改`，可以继续执行并在最终说明中列出判断依据。只要存在 `需确认` 项，先暂停并询问用户是否执行这些项；没有明确确认时，只处理 `可直接改`，把 `需确认` 和 `只建议` 放到跳过列表。

修改前给出一段执行简报，至少包含：

```markdown
| 发现项 | 分类 | 证据 | 计划动作 | 验证方式 |
|---|---|---|---|---|
| ... | 可直接改 / 需确认 / 只建议 | 文件/调用链/数据源证据 | 改什么或为什么不改 | 测试/编译/仅建议 |
```

简报里的 `计划动作` 必须能追溯到证据；没有证据的项只能归为 `只建议`。如果简报和用户原始要求冲突，先停下来说明冲突点，不要继续改。

跳过以下发现，并在最终说明中标注：

- 修复会改变既有行为或兼容性。
- 修复需要大范围架构改造，超出用户指定范围。
- 证据不足，无法证明两个字段、数据源、工具方法或调用链等价。
- 风险高但缺少测试保护，当前任务只适合提出建议。
- 用户未确认的 `需确认` 项。

### 4. 应用改动

只修改已归类为 `可直接改`、或用户明确确认执行的发现项。每个改动都必须能追溯到第 3 步的分级结果。优先采用项目已有风格：

- 复用现有 helper/component，而不是新建单次使用抽象。
- 删除错误限制优先于新增 fallback。
- 批量读取优先于循环单查。
- 简单 getter、常量和清晰的一层方法调用可保持 inline；只有复杂表达式、复用值或有调试价值时才提取局部变量。
- Java DTO/VO/Request/Response 中存在 `zValue`、`pType`、`uId` 等 JavaBean/Jackson 高风险字段时，显式添加 `@JsonProperty`，必要时用 `@JsonAlias` 兼容历史字段，并补充聚焦测试。

### 5. 验证

根据改动风险选择验证方式：

- 纯删除死代码或局部重命名：至少运行相关编译或静态检查。
- 抽取公共逻辑：运行原有相关测试，必要时补充聚焦测试。
- 改批量查询、数据源或响应映射：用单测或最小可复现命令验证数据范围和返回字段。
- Maven 后端项目若 smart-doc 绑定早期生命周期，而目标只是验证业务代码，命令中优先加 `-Dsmart-doc.phase=verify`。

如果无法运行测试，明确说明原因和剩余风险。

## 输出格式

完成后用简洁中文汇报：

```markdown
已完成代码简化与重构。

本次范围：...
本次模式：报告模式 / 安全修复模式 / 确认后修复模式

执行前简报：已给出 / 不需要（原因）

已修改：
- ...

已跳过：
- ...（原因）

验证：
- ...
```

如果没有可安全修改的问题，直接说明代码在本轮范围内已经足够干净，并列出检查过的角度。

## 与其他任务的边界

- 用户要找 bug、回归、空指针、安全问题：优先使用代码审查或调试类 skill，而不是本 skill。
- 用户要按新需求开发功能：先完成需求实现，再用本 skill 做收尾清理。
- 用户要大规模模块重构：先做重构方案和风险拆解，再分批执行；本 skill 适合每一批改动后的清理闭环。
