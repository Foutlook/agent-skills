# TOB Weekly Review

## Purpose

把分散在需求、提交、PR、测试反馈和发布记录里的 TOB 研发信息，整理成一份可复盘的周报，并形成风险 action 闭环。

这个 skill 的目标不是泛泛总结提交，而是帮助开发负责人每周回答：

1. 本周业务推进到了哪里。
2. 当前核心后端工作和相关业务模块分别完成了什么。
3. 哪些跨仓库、跨模块、跨角色依赖需要关注。
4. 上周遗留动作哪些已完成，哪些仍在进行中，哪些需要继续跟踪。
5. 哪些风险要转成明确 action，并在下周回看。

## Guardrails

- 不要把当前后端工作重点写成 TOB 业务的全部边界。可以写“当前核心后端工作”“相关业务模块”“当前重点仓库”，不要写成“TOB 只包含某几个项目”。
- 不要按仓库机械堆提交。先按业务能力归类，再把仓库、分支、PR、提交作为证据。
- 不要把 AI 推断写成事实。没有证据的内容标为“待确认”。
- 不要只写完成事项。必须写风险、阻塞、下周动作和上周 action 回看。
- 不要编造 KPI、上线效果、事故结论或用户影响。没有明确材料时写“当前材料未体现”。
- 不要跳过候选 action 的生成前确认。生成本周周报前，必须先读取上周周报的“下周动作”；如果抽取到候选 action，必须询问用户哪些已完成、哪些进行中、哪些需要继续跟踪，完成项直接标注 Done 后再开始生成本周周报。若没有候选 action，则记录跳过原因并继续生成。
- 不要把 AI 自动推导的 action 直接当成最终下周动作。生成周报后必须进入人工确认环节，确认哪些已完成、哪些进行中、哪些需要下周关注和投入人力。
- 不要遗漏用户手动输入的待办事项。人工补充待办优先于 AI 候选 action；如果需要后续跟踪，只在最终“下周动作”中完整呈现。生成前补充的输入可在第 0.1 节记录处理去向；生成后补充的待办不得回填到第 0.1 节，只能在第 11.3 节记录新增并引用 action ID。
- 不要重复铺开同一待办。第 8 节“下周动作”是唯一完整待办清单；其它章节只写状态、来源、调整记录或引用 `A1/A2` 这类 action ID。
- 不要在找不到上周周报或无法解析“下周动作”时编造遗留事项。若已确认没有上周动作，直接记录“无上周遗留动作”并继续生成。

## Inputs

优先收集这些材料：

- 本周 git log、PR/MR、merge 记录、分支名。
- 本周需求文档、技术方案、测试反馈、发布记录。
- 本周线上问题、联调问题、阻塞点。
- 上周周报中的“下周动作”，用于生成前询问状态并形成本周回看。
- 生成前人工确认输入：仅当抽取到候选 action 时，确认上周下周动作中已完成、进行中、需要继续跟踪的事项。
- 下周计划、待发布版本、待评审方案。
- 生成初稿后的人工确认输入：已完成事项、进行中事项、下周关注事项、需要投入的人力 / 角色、手动补充输入或待办候选。

如果材料不足，先输出“可用材料”和“缺失材料”，再继续做保守版周报。

## Workflow

### 1. Determine Scope

确认本周范围：

- 周期：例如 `2026-W13` 或 `2026-03-24 至 2026-03-28`
- 业务范围：例如辅学教练工作台、掌握度/PT-Z、学习报告、新机批、错题本
- 技术范围：当前核心后端工作、相关前端/客户端、数据服务、测试发布
- 产物路径：默认 `doc/weekly/tob/YYYY-WW.md`

### 2. Pre-Review Last Week Actions

生成本周周报前，先定位上周周报并读取其中“下周动作”。

#### 2.1 Locate Last Week Report

定位顺序：

1. 如果用户给出上周周报路径，优先读取该文件。
2. 如果用户只给出当前周，按上一周编号查找周报文件，例如 `2026-W28` 先找 `2026-W27`。
3. 如果未给路径，优先在当前工作区这些目录查找：`work_report/`、`doc/weekly/tob/`、`doc/weekly/`、`docs/weekly/`、`doc/`。
4. 文件名候选包括 `weekly`、`周报`、`tob`、`TOB`、`YYYY-WW`、`YYYY年Www`。
5. 如果找到多个候选，列出路径和修改时间，请用户确认使用哪一份。

找不到上周周报时，先按“无上周动作”处理并继续生成保守版周报，不要阻塞流程；同时在第 0 节记录“未找到上周周报，本次跳过上周动作回看”。如果用户后续补充上周周报路径或动作原文，再回填第 0 节和第 7 节。

如果找到了上周周报，但没有“下周动作”段落，或该段落为空，直接跳过生成前确认：

- 在本周周报第 0 节写明“上周无下周动作，已跳过上周动作回看”。
- 在第 7 节写明“无上周遗留动作”。
- 继续收集本周材料并生成周报。

#### 2.2 Extract Next Actions

动作抽取规则：

- 优先找标题为 `下周动作`、`下周 Action`、`下周计划`、`Next Actions`、`Action Items`、`计划 / Todo` 的段落。
- 从命中的标题开始，读取到下一个同级或更高级 Markdown 标题为止。
- 同时支持 Markdown 表格、编号列表、无序列表和 `P0/P1/P2` 前缀。
- 尽量保留原文中的优先级、动作、Owner、预期结果、截止时间、状态和证据。
- 如果段落混有普通描述和动作，只抽取带有明确动词、负责人、优先级、状态或截止时间的候选项。
- 不要用本周 git log 反推上周动作已完成。完成状态必须来自用户确认或明确证据。

无法确定是否为 action 时，先作为“候选 action”展示原文，不要直接进入最终周报。

只有实际抽取到候选 action 时，才需要向用户确认状态。没有候选 action 时直接跳过确认并继续生成。

抽取到候选 action 时，必须先向用户确认：

```markdown
我先回看上周周报的“下周动作”，请确认：
1. 已完成 / 已上线 / 已关闭：
2. 仍在进行中：
3. 需要本周继续跟踪：
4. 需要手动补充到本周周报关注范围的事项：
```

确认后再继续生成本周周报：

- 已完成：在“上周 action 回看”中标记 `Done`，写明人工确认或证据。
- 进行中：在“上周 action 回看”中标记 `Carry Over`，并进入本周风险、测试发布关注点或下周动作候选。
- 继续跟踪：必须进入本周关注范围，并写清 Owner、下一步、截止时间或需要投入的人力。
- 手动补充事项：纳入本周证据收集范围，不能被 git log 自动摘要覆盖掉；如需下周跟踪，在第 8 节生成唯一 action ID，第 0.1 节只记录生成前输入的“已纳入 A*”。若事项是周报初稿生成后才补充，不得写入第 0.1 节。
- 无法解析：保留原文候选，标记 `待人工确认`，等用户确认后再决定是否纳入本周关注。

本周周报必须同时覆盖：

- 上周遗留问题的状态变化。
- 本周新增的业务进展、风险和证据。

#### 2.3 Confirmation Boundary

两次人工确认的职责不同，不能混用：

| 阶段 | 只确认什么 | 不做什么 |
|---|---|---|
| 生成前确认 | 上周“下周动作”的完成、进行中、继续跟踪状态，以及手动补充输入的处理去向 | 不确认本周新增风险的最终下周动作；不重复铺开手动待办详情 |
| 生成后确认 | 本周初稿中的新增进展、风险、阻塞、下周动作和人力投入 | 不把已在生成前确认完成的上周动作重新放回下周动作；不在人工确认记录中复制完整待办 |

补充边界：

- 第 0.1 节只记录“开始生成本周周报前”用户补充输入的处理去向。
- 周报初稿生成后，用户新增的待办属于生成后人工调整：第 11.3 节记录“新增 / A*”，如需跟踪则同步进入第 8 节唯一完整待办清单。
- 不得为了补齐记录，把生成后新增待办回填到第 0.1 节。

### 3. Gather Evidence

按来源提取证据，不要直接下结论：

- 需求证据：需求名、文档路径、关键目标、边界。
- 代码证据：仓库、分支、PR/MR、提交、关键类/模块。
- 测试证据：测试环境、回归结果、阻塞问题。
- 发布证据：发布分支、上线窗口、回滚风险。

推荐用表格记录：

```markdown
| 来源 | 证据 | 说明 |
|---|---|---|
| git | <repo>/<branch>/<commit> | <业务含义> |
| PR | #123 | <合入范围> |
| doc | <path> | <需求边界> |
```

### 4. Group By Business Capability

先按业务能力分组，再归纳仓库变更：

- 辅学教练工作台
- 虚拟教室 / 签到 / 公屏
- 实时监测 / 事件曲线 / 学生四分类
- 学习链路 / 掌握度 / PT-Z
- 错题本 / 学习报告 / 新机批
- 工程治理 / 服务隔离 / 发布联调

每组写清：

- 本周完成什么。
- 当前状态是什么。
- 依赖谁。
- 下周要推进什么。

### 5. Identify Risks

风险必须具体到机制，不要只写“有风险”：

- 跨仓库依赖未合齐。
- 接口契约或 DTO 字段未对齐。
- MQ / WebSocket / MQTT 边界不清。
- 幂等、重复投递、重试、补偿未验证。
- 统计口径或数据来源未确认。
- 大提交、模糊 commit message、缺少测试导致回溯困难。
- 联调、测试、发布、回滚路径不清。

每个风险先转成候选 action，不要直接写成最终下周动作：

```markdown
| 风险 | 影响 | Owner | Action | 截止时间 | 状态 |
|---|---|---|---|---|---|
| <风险机制> | <影响范围> | <负责人> | <下一步动作> | <日期> | Open |
```

### 6. Review Last Week Actions

如果存在上周周报，必须回看上周 action：

- Done：生成前已由用户确认完成，或已有证据关闭；写清证据。
- Carry Over：用户确认仍在进行中或需要继续跟踪；说明原因、新的截止时间和需要投入的人力。
- Dropped：确认不再做，说明原因。

### 7. Produce Weekly Markdown Draft

默认写入 `doc/weekly/tob/YYYY-WW.md`。如果用户没有授权写文件，先在对话中输出草稿。

输出模板见 `references/weekly-template.md`。

可以用脚本生成空白骨架：

```bash
python scripts/new_weekly_review.py --week 2026-W13 --out doc/weekly/tob/2026-W13.md
```

### 8. Human Confirmation Gate

周报初稿生成后，还要再次请用户确认本周新增事项。不要把初稿状态当最终状态。

需要向用户确认：

1. 哪些事项已经完成、验收、测试或上线。
2. 哪些事项仍在进行中。
3. 哪些事项需要下周继续关注。
4. 哪些事项需要投入人力，以及需要哪些角色投入。
5. 是否有手动补充的下周待办事项。

确认后再更新周报：

- 已完成事项：从风险、阻塞、下周动作中关闭或移除，必要时转入“需要沉淀的文档 / 方案 / 复盘”。
- 进行中事项：保留在风险、测试发布关注点或下周动作中，并写清 Owner、投入人力、截止时间和预期结果。
- 下周动作：只保留人工确认后仍需要跟踪和投入的事项；不要保留已经完成的归档项。
- 手动待办：如需后续跟踪，补入第 8 节“下周动作”并标记来源为“人工补充”；第 11.3 节只记录“新增 / 更新 / 移除”和对应 action ID；不得回填到第 0.1 节。
- 下周关注与人力投入：第 11 节只按 action ID 写确认摘要，不复制第 8 节的完整动作、Owner、预期结果。

推荐确认问题：

```markdown
请确认这几类事项：
1. 已完成 / 已上线 / 已关闭：
2. 仍在进行中：
3. 下周需要关注并投入人力：
4. 需要补充到下周动作的手动待办：
```

### 9. Final Check

交付前检查：

- 周报是否按业务能力组织，而不是只按仓库列提交。
- 每个关键结论是否有材料或代码证据。
- 是否避免把当前重点仓库写成 TOB 全部边界。
- 是否包含风险表和 action 表。
- 若抽取到上周“下周动作”候选 action，是否在生成本周周报前完成人工确认。
- 若找不到上周周报或没有上周动作，是否已记录跳过原因并继续生成。
- 是否包含上周 action 回看，并按 Done / Carry Over / Dropped 标注。
- 是否有人工确认记录。
- 下周动作是否只包含人工确认后仍需跟踪和投入的事项。
- 用户手动输入的待办事项是否已进入第 8 节唯一待办清单，且第 0 / 第 11 节仅引用 action ID、没有重复完整描述。
- 周报初稿生成后才补充的待办是否没有出现在第 0.1 节。

## Output Contract

最终输出一份 Markdown 周报，至少包含：

1. 本周核心结论
2. 本周业务进展
3. 当前核心后端工作进展
4. 跨模块 / 跨仓库依赖
5. 风险与阻塞
6. 测试与发布关注点
7. 上周 action 回看
8. 下周动作
9. 需要沉淀的文档 / 方案 / 复盘
10. 证据索引
11. 人工确认记录

如果是第一次落地这个流程，可以先产出第 0 期试运行周报，并在结尾标记“流程试运行”。
